# Terraform 工单聚合回复模板

适用于每次主处理 run 的 RD finalizer 唯一聚合回复，包括 done、idle、suspend、补料、
无须开发和恢复后的收口。executor 托管时完整正文写入 `AONE_RESULT.reply_body`；独立
finalizer 使用相同正文。后续 PR、催办、失败等生命周期事件继续使用各自的固定通知模板。

## 固定正文

必须按下面四段的标题和顺序输出，段落之间留一个空行。替换所有占位内容，不要把整个
回复包进代码块。前三段的总结句必须加粗；无待办、未进入发布阶段或证据不可用时也保留对应段。

```markdown
**一、完成情况**

**总体进展：<一句话说明需求当前走到哪一步，已经交付什么，尚缺什么>。**

资源构建：<已完成／进行中／未开始／无需变更／未确认>；<已完成的具体范围>。

资源测试：<已通过／部分通过／未通过／未开始／不适用／未确认>；<测试范围及真实结果>。

资源文档：<已完成／进行中／未开始／无需变更／未确认>；<已完成的具体范围>。

Provider 发布：<待评审／待合并／待发布／已发布／无需发布／未确认>；<实际版本或剩余发布前提>。

**二、待处理事项及负责人**

**当前待办：<谁需要完成或确认什么；确实无待办时写“无”>。**

处理人：<职责／团队> <已核实的姓名及 @花名(工号)；未知时写“负责人待确认”>。

处理内容：<具体工作或需要拍板的问题；需选择方案时写清各选项差异，并附方案链接>。

下一步：<该事项解决后推进哪一步；有已确认完成时间时注明>。

**三、预计发布时间**

**发布安排：<已确认的预计发布时间；或“待发布，发布时间待确认”；或“尚未进入待发布阶段”；或“无需发布”；或“已发布：版本及日期”>。**

依据／待确认事项：<排期确认来源与链接；或发布尚待谁确认、满足什么条件>。

**四、必要证据**

<仅列有助于判断的查证结论、改动范围、评审链接、构建及测试结果、可视化报告链接；详细技术材料放链接中>。
```

## 填写规则

- 以需求方和前线能判断进展为准，不按 PD/RD/QA 分段，不输出内部路由字母、handoff、
  ledger、outcome 等流程术语。内部查证、开发、验收结果需要综合后翻译成上述业务状态。
- 构建、测试、文档、发布分别判断，不能用“代码已写”代替测试通过，不能用“PR 已开”
  代替评审完成，也不能用“PR 已合并”代替版本已发布。仅预发验证不算正式发布。
- 百分比仅在范围及分子分母明确、有证据时使用，并同时展示计数，例如“计划 10 项验收，
  已通过 2 项（20%）”。没有依据时只写真实状态，不估算百分比；部分测试通过不能表达成
  整个需求已完成同样比例。未执行不写已通过，不适用与未确认必须区分。
- 已确认待发布的需求必须交代发布时间；没有已确认排期写“待发布，发布时间待确认”，
  并说明待确认的负责人或条件。不得把需求期望日期、惯常发版周期或推测当作发布承诺。
  不知道负责人时明确“负责人待确认”，不得编造姓名、工号、@ 或日期。
- 多个待办分别重复“处理人／处理内容／下一步”，明确每个人负责什么。确实没有待办时
  写“当前待办：无”，无需留下空的处理人字段；缺少材料或能力也是待办，须写清补什么、
  谁来补。未经核实不得宣称已通知、已改派或已完成外部动作。
- 必要证据保留查证结论、RD 改动及 MR/CR、CI、QA 验收与三层报告的可用证据；正文只
  解释其对需求的影响，不粘贴长日志、源码或全部排查过程。链接使用 `[说明](URL)`。
  截图或上传失败时简述“可视化报告暂不可用：<原因>，本次依据<文字证据>”，详细错误
  分类留在内部记录；不得因此省略回复或改变业务 outcome。
- 无开发需求、补料、挂起和恢复场景仍使用四段；无需变更／不适用必须有已查明的原因。
  缺失的证据写“未确认”及缺口，不为填满模板编造信息。
