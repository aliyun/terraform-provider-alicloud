# 写周报 skill（本仓 vendored）

> 这份 skill 沉淀自 2026-06-26 的一次真实迭代：AI 草稿 → 用户大幅精简改稿 → 对照差异得出的"周报应当怎样写"。Gold standard 是辰羿本人最终交付到钉钉文档的版本。

## 定位（与 a1 中心同名 skill 的关系）

a1 skill 中心已有同名 `writing-weekly-report` 及若干同类（`my-weekly-report` / `auto-weekly-report` / `ei-internal-doc-writer` 等），偏**数据自动采集**（10 大数据源、自迭代风格学习）。

本仓 vendored 版偏**风格规范 + 对照表**：
- ✅ 辰羿本人的钉钉文档输出格式（`**粗体**` + `-` + 裸 Aone 号 + `:::`）
- ✅ "价值视角不是仓库视角"等核心原则
- ✅ "AI 草稿 vs 用户终稿"对照表（持续迭代沉淀经验）
- ⛔️ 不重复造采集 10 数据源的轮子（钉钉日历/AI 听记/语雀等），那些由 a1 中心 skill 解决

加载优先级：本仓 `.claude/skills/` 覆盖全局 `~/.claude/skills/`，本仓版本生效。如需自动化采集，可手动调用 a1 中心 skill 配合本仓的格式规范。

## 一、何时用

触发词（中文为主，英文也算）：
- "写周报"、"做周报"、"做个汇报"、"做月报"
- "总结/汇总下我（最近 / 这周 / 近两周 / 近一个月）的工作"
- "把工作更新到（钉钉文档/这个链接）"且链接内容是周报性质
- 用户给了同事/老板的范本，要求按那个风格写
- 用户说"参考 xxx 风格"+ 时间窗口词

不触发的：
- 单条工单回复（走 aone-triage）
- PR 评审报告（走 terraform-pr-review）
- 单次任务完结回报（走 wrap done 即可）

## 二、核心原则（先于格式）

### 原则 1：价值视角，不是活动视角

- ❌ **不按仓库分块**：cloudspec / automation_agent / acube 各写一段——读者（老板/外部协作）看不出"你交付了什么对外价值"
- ✅ **按对外可交付价值分块**：例如"MCP Server RunIaC 上线" / "工具体系对内门户 PlayGround 上线" / "Terraform AutoPilot 能力建设"
- 同一个价值方向横跨多个仓的工作要**合并写**

### 原则 2：基础设施工具不当主线

- 像 Jarvis 自治系统、a1id 多身份切换器、钉钉桥这类内部支撑工具，**不要展开技术细节**
- 写"用它交付了多少需求"，而不是"我搭了什么模块"
- 范例：
  ```
  **Terraform AutoPilot 能力建设**
  - **Jarvis 自治系统从 0 到 1**：从零搭建,covers ...全链路;具备无人值守 triage 到预发的闭环能力。
  - 目前近一周多个需求已通过 Jarvis 交付。
  ```
- 200+ commits 的内部建设 → **压缩到 1-2 行**

### 原则 3：粒度纪律

| 项 | 上限 |
|---|---|
| 一级方向数 | **3-5 个**，绝不超过 7 |
| 每个方向的子项数 | 2-4 个 |
| 每个子项 | 1 行（一句话讲完） |
| 杂项工单（一次性修复、版本升级、小蜜单条） | **默认不写**，除非属于本周主线价值 |

### 原则 4：状态词标准化

- **已上线 / 已合入 / 已 merged / 已通过预发验收 / 已闭环**
- **开发中 / 验收中 / 评审中 / 联调中**
- **待合 / 待 prod / 待预发腾空 / 待人工合并**

不要用模糊词："基本完成"、"差不多了"、"在推进"。

### 原则 5：保留关键标识

- 分支名精到 `feature/YYYYMMDD_<工单号>_<short-name>`（这是 a1 codeup 的标准命名，体现工单溯源）
- CR/MR 号：`!28216363`、`CR !28205668`
- Aone 工单号：**裸号即可**，钉钉文档里 markdown 链接渲染丑，老板看裸号反而清爽
- 对外发布物（GitHub PR 等）：**带 markdown 链接**，方便老板点开

### 原则 6：进度百分比可选

- 同事样例（金子超/苏铂）用 `进度 X% from Y%`——量化进度，适合大方向
- 辰羿终稿全部去掉——偏好简洁
- **默认不写**；用户明示要"参考 xxx 风格"且范本有这种格式时再加

## 三、数据采集（按顺序，分层归纳）

不要把全部原始数据塞给用户。**先归纳，再呈现**。

### 3.1 本仓优先：jarvis 自带的数据源

```bash
# 1) git 提交（按时间窗口）
git log --since="YYYY-MM-DD" --pretty=format:"%h %ad %s" --date=short --no-merges

# 2) runs/ 台账（jarvis 完工记录,带摘要+MR/CR链接）
ls -lat runs/
for f in runs/<window>*.md; do echo "== $f =="; cat "$f"; done

# 3) escalation/ 待办（escalate 的工单）
ls -lat escalation/

# 4) 周报真源工具(如存在,优先用)：基于 Aone jarvis-done 标签出清单
bootstrap/week.sh
```

### 3.2 跨仓数据：a1 events user

`a1 events user` 是周报跨仓最强工具——拿任意工号在所有仓的活动事件。

```bash
# 工号查询（花名 → 工号）
bin/a1id -- staff list <花名>

# push 事件（看每个仓动了哪些分支）
bin/a1id -- events user <工号> --since YYYY-MM-DD --until YYYY-MM-DD --per-page 100 --type push

# MR 事件（看 CR 创建/合并节奏）
bin/a1id -- events user <工号> --since YYYY-MM-DD --until YYYY-MM-DD --per-page 100 --type merge-request
```

注：默认 `bin/a1id`（jarvis 身份的底层就是辰羿本人 320687）即可查辰羿/ChenHanZhang/jarvis 这三个等价身份的所有活动；查其他人（如服务账号 `open-jarvis`）也用同样方式。

### 3.3 关联仓库范围

只关心 `config/workspaces.json` 登记的仓；其他仓**不汇报**——别的仓不归我们。

### 3.4 身份去重

辰羿日常署名跨多个 ID，写周报前先对齐：
- `辰羿` / `ChenHanZhang` / `jarvis` / `chenhanzhang.chz` — **同一人**（工号 320687）
- `open-jarvis`（WORKER_xxx，邮箱 `open_jarvis@alibaba-inc.com`）— **独立服务账号**，写在"服务账号代发 CR" 子项里
- `Jarvis 代码账号`（蚂蚁内部 `admin.for.jarvis@antfin.com`）— 与本工作线无关，不写

## 四、输出格式（钉钉文档版，gold standard）

钉钉文档的 markdown 渲染特殊性：
- **一级方向用 `**xxx**`（粗体段落）作为标题**，不要用 `#`/`##`/`###`——钉钉的标题视觉过重，把简洁感破坏
- **二级用标准 `-` bullet**，不要用 `●`/`○`/`■` 字符 bullet
- 整篇可用 `:::` 包一层钉钉容器块（可选）
- 表格慎用（`[...]`/`{...}` 会被钉钉当 checkbox/链接吞掉）

### 模板（辰羿 2026-06-26 终稿同款）

```
:::
# **重要事项**

**<价值方向 1>**
- **<子项 1>**：<细节,带分支名/CR号/工单号/状态词>
- **<子项 2>**：<...>
- **<子项 3>**：<...>

**<价值方向 2>**
- **<子项>**：<...>

**<价值方向 3：能力建设>**
- **<内部工具 X>**：<一句话简介,不展开技术细节>
- 目前近一周多个需求已通过 <X> 交付。
:::
```

### 同事范本风格（详细版,可选）

参考金子超/苏铂的样例——量化进度+三级展开。仅当用户**明示**要"参考 xxx 风格"+范本有这种细节时使用：

```
● **<方向>**，进度 X% from Y%。
    ○ <子项>: <细节>
    ○ <子项>: <细节>
        ■ <三级展开,带数据>
        ■ <三级展开>
```

## 五、写入流程

1. **数据采集**：3.1 → 3.2 → 3.3 → 3.4，归纳出候选价值方向
2. **草稿先出文本**：在对话内呈现 markdown 草稿，**不要直接写入文档**
3. **用户确认/调整**：用户可能大幅删减、合并、改方向名——以用户终稿为准
4. **如指定钉钉文档 URL**：调 `dingtalk-doc-rw` 的 `update_doc`（覆盖式）写入
5. **回读校验**：`read_doc` 拉回内容，目测渲染没炸（粗体、bullet、链接、`:::` 容器都正常）

如果用户没指定文档，**草稿即终稿**，直接输出给用户。

## 六、对照表：AI 草稿易写错的 vs 终稿保留的

> 这是本 skill 沉淀的核心经验。每次写完草稿后，按这个表自检一遍再呈交。

| 草稿（AI 容易写的） | 终稿（用户保留的） | 为什么 |
|---|---|---|
| 按仓库分块，每仓一个一级 | 按价值方向分，跨仓合并 | 读者关心交付价值，不是技术活动 |
| 7-8 个一级方向，面面俱到 | 3-5 个一级方向 | 老板不读冗长清单 |
| Jarvis 自治写 6 个子项展开 | Jarvis 一句话 + "交付了 N 个需求" | 工具是杠杆,价值是产出 |
| 列所有杂项工单（FC 日志/版本升级/小蜜单条） | 删杂项，只留主线 | 噪声拖垮重点 |
| 每条都带 `[Aone 8xxxx](url)` markdown 链接 | 裸 Aone 号即可 | 钉钉里链接渲染丑 |
| 加"未完待办"段 | 不加 | 老板不关心你的 TODO |
| 加"其他工单交付"段 | 不加 | 同上 |
| 一级用 `●` 字符 | 直接 `**粗体**` | 钉钉原生 markdown 更干净 |
| 二级用 `○` 字符 | 标准 `-` | 同上 |
| 每条加"进度 X% from Y%" | 默认不加 | 辰羿偏好简洁 |
| 一级标题用 `### xxx` | 用 `**xxx**` 段落 | 钉钉 `###` 视觉过重 |

## 七、红线

1. **不带 AI 署名**：周报对外，**禁止**出现「🤖 Generated with Claude Code」「Co-Authored-By: Claude」等任何 AI 水印（CLAUDE.md 纪律 7）；commit / PR / 钉钉文档正文都不带。
2. **回读校验**：钉钉文档写入后必须 `read_doc` 回读，确认渲染正常——钉钉的表格、嵌套 bullet、链接都有坑。
3. **草稿先于写入**：除非用户当面授权直接写文档，否则草稿在对话内呈现，等用户确认。
4. **不擅作主张挖人/挖工单细节**：周报里出现的 Aone 号、工单标题、人名，都必须来自实际数据采集结果，不能脑补凑数。

## 八、调用示例

### 调用 1：仅出草稿

> 用户："汇总下我近两周的工作"

步骤：
1. 跑 3.1 + 3.2 拿数据
2. 归纳 3-5 个价值方向
3. 按"四、输出格式"出 markdown 草稿
4. 在对话内呈现

### 调用 2：草稿 + 写入钉钉文档

> 用户："汇总下近两周工作，更新到 https://alidocs.dingtalk.com/i/nodes/xxxxx"

步骤：
1. 跑 3.1 + 3.2 拿数据
2. 归纳
3. 出草稿
4. **先 `read_doc` 看目标文档是否已有内容**——空则覆盖，非空则与用户确认追加 / 覆盖 / 改写
5. 调 `update_doc` 写入
6. 调 `read_doc` 回读验证

### 调用 3：参考同事范本

> 用户："参考 xxx 周报样式写一份"

步骤：
1. 用户给的范本——分析格式（量化进度？三级展开？方向命名习惯？）
2. 按范本风格生成草稿（可启用"详细版"格式）
3. 出草稿
4. **预期用户会再改一轮**——按用户终稿迭代，don't argue

## 九、维护

每次写完周报后，如果用户终稿与草稿有**系统性差异**（不只是单次微调），把新经验回写到"六、对照表"。本 skill 应随每次迭代变得更准。
