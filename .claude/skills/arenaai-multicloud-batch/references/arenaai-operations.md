# ArenaAI 页面操作与恢复

## 页面基线

先从当前页面可见状态确认控件，不盲目依赖历史选择器。当前 ArenaAI 页面通常可通过以下线索识别：

- 输入框：`textarea[placeholder="输入问题，即刻开始"]`
- 发送按钮：`button[class*="submitBtn"]`
- 用户消息：`.user-message`
- 对战回答：`.battle_assistant`

站点更新后选择器可能变化。若选择器失效，先读取可见 DOM、标签、占位符和按钮状态，再做最小调整；不要通过读取站点存储或注入到无关页面来恢复。

## Chrome 控制顺序

1. 使用 `chrome:control-chrome` 提供的浏览器客户端完成选择、命名会话、导航和交互。
2. 如果 ArenaAI SPA 的 DOM/交互调用持续超时，先读取 Chrome 技能的故障排查文档，并使用它列出的替代能力。
3. 只使用当前 `chrome:control-chrome` 技能明确允许的浏览器控制接口，不切换到 Apple Events、独立自动化服务器或其他浏览器技能。
4. 若允许的接口无法创建独立 Chrome 窗口，向用户说明限制并请用户创建或激活一个新窗口后继续；不要静默换成内置浏览器或改造无关窗口。

## 稳定台账

不要仅使用“第几个标签页”作为身份，因为标签页会重排。为每个目标页维护：

```text
stable_tab_id
question_index
question_text
normalized_question_hash
pre_submit_user_message_count
pre_submit_answer_count
state
retry_count
attempt_started_at
```

每次重载或重新绑定标签页后，先用稳定 ID 和可见 URL/标题校验目标；无法证明是原目标页时停止，不猜测 ID。

## 填入问题

React 控制的文本框可能不会响应简单的 `element.value = ...`。在已经确认目标元素正确时，可使用原生 setter 并触发输入事件：

```js
const textarea = document.querySelector('textarea[placeholder="输入问题，即刻开始"]');
const setter = Object.getOwnPropertyDescriptor(
  HTMLTextAreaElement.prototype,
  'value'
).set;
setter.call(textarea, question);
textarea.dispatchEvent(new InputEvent('input', {
  bubbles: true,
  inputType: 'insertText',
  data: question,
}));
textarea.dispatchEvent(new Event('change', { bubbles: true }));
```

填入后再次读取 `textarea.value`，要求与原问题完全一致；再确认发送按钮未禁用。不要在同一个脚本事件循环中立即点击，给页面状态一次更新机会。

## 幂等发送

发送前按以下顺序判断：

1. 将分配问题和页面中每条用户消息都做 Unicode 标准化、首尾去空白并折叠连续空白；若存在全文精确匹配，视为已提交，不点击。
2. 不存在匹配消息，且输入框内容与分配问题按同样规则精确匹配、按钮启用：可以点击一次。
3. 输入框已清空但没有匹配用户消息：状态不确定，等待并重新读取，不推断成功。
4. 输入框非空但按钮禁用：等待一次页面状态更新；仍禁用则诊断页面，不强制点击。
5. 没有输入框或按钮：页面尚未就绪或 UI 已变化，重新检查可见状态。

不要因为一批操作超时就再次点击整批。超时可能发生在点击已经生效之后。

## 状态定义

为每页记录以下状态：

- `prepared`：输入框内容与分配问题完全一致，发送按钮可用。
- `submitted`：出现与分配问题规范化后全文精确匹配的用户消息。
- `generating`：已提交，页面仍显示停止生成控件或“生成中，请等待”等明显状态。
- `completed`：已提交，准备前回答基线之后新增至少一个与该问题关联的回答容器且包含有意义正文，而且生成控件已经消失或恢复为普通的禁用发送按钮。
- `failed`：出现 `Failed to fetch`、明确错误提示、空白结果且不再生成，或长时间无进展。

“有意义的正文”应明显超过模型标签或占位符。可将 100 个可见字符作为普通问答的保守下限，但应结合页面内容判断；不能仅凭回答容器存在、投票按钮出现或 `A/B` 标签出现认定成功。

生成中的按钮目前可能含有 `Stop Loading` 标题；完成后按钮通常回到普通发送图标并因输入为空而禁用。站点变化时以可见语义为准。

## 轮询与恢复

- 正常轮询间隔为 15–30 秒。记录回答长度；只要长度持续增加，就继续等待。
- 生成超过 90 秒且连续两次长度不增长，可视为卡住。
- 每次提交或恢复尝试设置 6 分钟墙钟期限；即使文字仍增长，到期也停止无限等待，保留页面并报告状态。用户要求继续等待时再延长。
- 若同一批中至少 3 页或 20% 页面出现相同的鉴权、限流或服务错误，立即暂停新的发送和重试，等待 60 秒后复查一次；仍为系统性错误时停止批量重放并报告。
- `Failed to fetch`：等待其他页面完成以降低负载，然后在原页重新填入同一问题并重发一次。
- 空白结果、发送按钮无法重新启用或生成卡死：只重载该页，等待输入框恢复，再填入原问题并重发。
- 重试前必须检查是否已经出现用户消息或有效回答，避免重复。
- 每页最多 2 次恢复性重试；超过上限后保留页面并向用户报告，不循环刷新。

## 最终验收

最后一次全量扫描必须重新读取每个目标页面，而不是依赖早先的点击返回值。至少汇总：

```text
目标页面数
唯一分配问题数
已提交数
精确匹配的用户问题数
含有效回答数
已停止生成数
待处理页码
发生过恢复性重试的页码
```

只有四个核心计数都等于目标页面数且待处理为空，才能报告全部成功。
