# 问题设计规则

## 目标

生成数量精确、语义互异、覆盖面均衡的问题集。这里的“随机”指从不同主题、生命周期阶段、云厂商组合和决策视角交叉取样，而不是简单替换名词。

## 主题池

从下列主题池交叉选择。用户明确点名的主题和云厂商优先于默认配额。未指定比例且 `N >= 10` 时，按主类别使用约 30% Terraform、20% CCAPI、20% aliyun CLI、20% 多云横向对比、10% 企业 IT 治理；四舍五入后通过增减最大类别使总数精确等于 `N`。数量更少时优先覆盖用户点名的类别。

1. **Terraform 工程与生命周期**
   - 模块边界、仓库结构、Provider 版本、state 拆分与保护
   - import、漂移检测、升级迁移、回滚、测试、CI/CD、供应链安全
   - 多团队协作、权限模型、成本估算和策略即代码
2. **CCAPI 与声明式资源接口**
   - AWS Cloud Control API、Terraform Provider、原生 SDK 和模板服务的选型
   - Schema 覆盖度、异步操作、幂等、错误模型、状态读取和版本兼容
   - Azure ARM、GCP Config Connector、阿里云 ROS/资源 API 与 AWS CCAPI 的比较
3. **aliyun CLI 运维与自动化**
   - Profile、Region、STS/RAM Role、最小权限和凭证轮换
   - 输出过滤、分页、幂等脚本、错误诊断、审计和 CI 集成
   - `aliyun` CLI 与 Terraform、ROS、SDK 在临时运维和长期纳管中的边界
4. **多云横向对比**
   - AWS、Azure、GCP、阿里云的组织层级、IAM、网络、策略、日志和成本体系
   - 账号/订阅/项目划分、区域与可用区差异、服务配额、资源标签和统一抽象
   - 比较时说明业务场景和评价维度，避免泛泛询问“哪个更好”
5. **企业 IT 治理**
   - 组织基线、例外审批、合规映射、数据驻留、FinOps、审计和可观测性
   - 平台团队、安全团队、财务团队和业务团队的职责边界
   - 存量纳管、并购整合、服务目录、自助交付和治理成熟度演进

## 多样性矩阵

为每个问题选择不同的组合：

| 轴 | 可选值示例 |
|---|---|
| 生命周期 | 设计、部署、变更、迁移、故障恢复、审计、退役 |
| 视角 | 架构、平台工程、安全、合规、FinOps、运维、开发体验 |
| 范围 | 单云内部、两云对比、四云对比、中央平台与业务团队协作 |
| 问题类型 | 设计方案、选型标准、差异分析、故障诊断、治理流程、度量指标 |

避免连续问题使用相同的“主题 + 生命周期 + 视角”组合。对云厂商组合进行轮换，不要让所有横向问题都以 AWS 为中心。

生成时维护一张临时清单，至少包含：`编号 | 主类别 | 生命周期 | 视角 | 云厂商集合 | 问题全文`。检查主类别计数满足用户要求或默认配额；企业治理也可作为其他主类别的次级视角，但同一问题只计入一个主类别。

## 质量检查

- 每条通常为一句完整问题，必要时可加一个约束句。
- 必须能产生有分析价值的回答，避免纯定义题和只有“是/否”的问题。
- 不把同一问题通过交换云厂商顺序、替换同义词或增加“企业级”前缀伪装成新问题。
- 除全文去重外，还要比较核心对象、决策目标和约束条件；三者相同的近义问题只保留一条。
- 去除重复后数量仍必须等于 `N`；不足时从尚未覆盖的矩阵组合补充。
- 不要求模型访问内部系统、执行命令、泄露配置或生成真实凭证。

## 问题形态示例

以下是形态示例，不是固定题库；每次应重新组合主题和约束：

- 设计型：如何为某类多云资源设计可演进的 Terraform 模块边界，并处理云厂商差异？
- 选型型：在什么条件下应选择 CCAPI、Terraform Provider、原生 SDK 或模板服务？
- 对比型：四家云的组织策略继承模型差异会怎样影响统一治理基线？
- 运维型：aliyun CLI 在跨账号批量操作中如何实现最小权限、幂等和可审计性？
- 故障型：Provider 或 CCAPI 返回不透明错误时，怎样建立不会泄露敏感信息的诊断流程？
- 度量型：多云 IaC 平台应使用哪些 SLI/SLO 衡量交付效率、稳定性和治理效果？
